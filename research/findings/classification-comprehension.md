**Academic work:**
- **Refactoring detection.** RefactoringMiner 2.0 detects more than 40 refactoring types with **99.6% precision and 94% recall** (TSE). It covers Java, and there are ports for Python and JS. This is the strongest published accuracy for a deterministic "refactor-only" label. https://github.com/tsantalis/RefactoringMiner , https://arxiv.org/abs/2103.11563
- **JIT defect prediction.** Kamei 2013 uses 14 change metrics: size, diffusion, history, experience. DeepJIT reports roughly +10–14% AUC over its baselines (https://soarsmu.github.io/papers/2019/Hoang2019DeepJIT.pdf). JITLine reports +28–73% AUC and runs 70–100x faster than the deep models (https://arxiv.org/abs/2103.07068). ISSTA'21 found that a simple model using Kamei-style features is competitive with the deep ones ("Deep JIT-DP: How far are we?"). These models output **defect probability, not a change type**.
- **Intent classification.** Levin & Yehudai 2017 classify changes as corrective, adaptive or perfective from the commit message plus code-change features (https://arxiv.org/abs/1711.05340). Trautsch et al. 2022 did the same with a fine-tuned NLP model (https://arxiv.org/abs/2109.03544). These rely on commit messages, which an AI author can write in a misleading way.

**Takeaways for A:**
1. In practice, auto-approval is driven by **deterministic, narrow** types: docs, tests, formatting, clean revert, semver patch, generator-produced changes. The ML scores (DRS, JIT-DP) answer "how risky is it", not "what kind of change is it".
2. **Provenance is a type.** Google, Chromium and Spotify trust a change because *a vetted tool produced it*. The diff itself is not what earns the trust.
3. Calibrated confidence is rare. Mend uses crowd test outcomes, and RefactoringMiner uses an oracle benchmark. Nobody publishes calibration for an LLM label.

**Research:**
- **Bacchelli & Bird (ICSE 2013).** Defects are the motivation for review, but *understanding* is the main need, and current tools mostly don't meet it. https://www.microsoft.com/en-us/research/publication/expectations-outcomes-and-challenges-of-modern-code-review/
- **SmartBear/Cisco.** Based on 2,500 reviews: about 200–400 LOC per review, under 500 LOC/hour, 60–90 minutes per session. [vendor] https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/
- **Eye tracking.** Uwano 2006 and Sharif 2012 found that reviewers who do an initial **full scan** find defects faster. That supports showing an overview first, then the detail. https://arxiv.org/pdf/2103.08777 (survey)
- **AI-assisted code and comprehension.** A study on arXiv 2601.20245 reportedly found that people who delegated fully scored below 40% on comprehension, while those who used AI for explanations scored above 65% [UNVERIFIED]. Gao et al. (Jul 2026, N=34) reportedly found that explanation level changes trust and agreement but not review time [UNVERIFIED]. Spinellis' blog "why reviewing AI-generated code is devilishly hard" https://www.spinellis.gr/blog/20260523
- **Learning science.** No code-review tool was found that applies retrieval practice, spaced repetition, worked examples or dual coding explicitly. Quiz gates are crude retrieval practice. The CodeRabbit diagram-plus-text layout is incidental dual coding. Chunking appears as stacked PRs (Graphite) and as Change Stack layers.

## C) The gap

| Capability | Exists? |
|---|---|
| Deterministic change-type labels | Yes but fragmented: gitStream, Rubber Stamper, Renovate, RefactoringMiner |
| Calibrated confidence per label | Only Mend (deps) and RefactoringMiner (benchmark) |
| Risk tiers / auto-review funnel | Yes: RADAR, Cloudflare, Iron |
| Checks per stage or per type | Partly: Rubber Stamper per type, RADAR funnel |
| Comprehension aid **scaled to the tier** | **Not found.** Walkthroughs and quizzes look the same for every PR |
| Reviewer-side (not author-side) comprehension check | **Not found as an enforced gate.** CodeRabbit's 5 questions are advisory |
| Named, accountable sign-off that records what was understood | **Not found.** Gerrit and GitHub record *who* approved. Change Stack snapshots *what* was reviewed. Nobody records *what the reviewer showed they understood* |

**Verdict.** The hypothesis holds, with one refinement. The individual pieces exist. What nobody does is the **chain**: (1) a deterministic type label from AST, refactoring detection and paths, with calibrated confidence, plus provenance, feeding (2) type-specific checks, for example a refactor-only label verified by RefactoringMiner plus "no behavioural diff", then (3) a comprehension layer that scales with the tier: nothing for docs, an overview plus diagram for low tiers, and a reviewer quiz on the *risky hunks* for high tiers, then (4) a signed attestation that binds the named reviewer, the commit SHA, the tier, and the comprehension evidence.

Prior art to cite as foundations: Rubber Stamper (deterministic per-type bypass), Mend (calibrated confidence), RAID (refactor-aware diff reduces load), and Change Stack (closest competitor on comprehension, but advisory only).

Risks to handle:
- Quiz gaming by AI. Mitigate by generating questions from the diff in ways an LLM paraphrase can't trivially answer, and by keeping them short and tier-gated.
- Mislabelled "safe" types. Have every check fail closed to a human reviewer, as RADAR does.
